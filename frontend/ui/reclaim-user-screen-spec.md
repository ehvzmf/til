# 자원회수 유저 화면 스펙

시각 기준은 같은 폴더의 `reclaim-user-mockup.html`이다. 구현 전에 브라우저에서 열어 맞춰 볼 것.
목업 상단의 `목업 옵션`으로 기본 상태와 빈 상태를 전환할 수 있고, 리소스명을 누르면 상세 패널이 열린다.
목업의 이름, 수치, 날짜는 모두 샘플이다.

## 1. 개요

- 자원관리 계정 앱의 회수 기능 중 **유저 대상 화면**이다. 관리자 화면(정책 관리, 선정 이력, 실행 이력)과는 별개다.
- 유저가 보려는 것은 "내 리소스 중 무엇이, 언제, 왜, 어떻게 되는가, 내가 무엇을 할 수 있는가"이다.
- 이 화면은 **현황을 보여주고 알맞은 곳으로 보내는 화면**이다. 조치 자체는 다른 서비스에서 일어나며 이 화면에는 조치 로직이 없다.

## 2. 용어와 규칙

- 위계: 계정 › 프로젝트 › 리소스.
- 회수 사유와 예정 조치(아무 조치도 안 했을 때의 결과)는 항상 한 쌍으로 표시한다.
  - 미사용 → 삭제
  - 한도 초과 → 회수
  - 사용률 저조 → 최적화
- 선정 주기, 회수 배치, 재평가 주기는 정책의 cron으로 돈다. 유저가 조치해도 회수 예정은 바로 해제되지 않고 **다음 재평가**에서 판단된다.
- 조치한 건의 재평가는 회수 배치보다 먼저 실행되는 것으로 가정한다.
- 유예 기능은 없다. 유저의 조치가 곧 유예 역할이다.
- 예외 신청은 관리자 화면에서 한다. 유저 화면에는 `예외가 필요하면 관리자에게 문의하세요` 안내 문구만 둔다.
- 목록은 로그인한 유저의 권한이 있는 리소스만 내려온다. 화면에서 권한 체크는 하지 않는다.

## 3. 화면 구조

- 네비게이션의 `자원회수` 독립 메뉴다. 진입하면 바로 이 화면이 나온다.
- 상단에 제목과 한 줄 설명을 둔다.
- 탭 두 개: `회수 예정 N`(기본), `처리 이력`.
- 리소스 상세는 오른쪽에서 열리는 패널(너비 480px)이다. 오버레이를 누르거나 Esc나 × 버튼으로 닫는다.
- 조치 버튼은 모두 **다른 서비스로 이동하는 링크**다. 링크 버튼에는 `↗`를 붙여 이동임을 드러낸다.

## 4. 회수 예정 탭

### 4.1 요약 카드 (4개, 4열 그리드)

- `미사용 → 삭제`: 건수와 최단 D-day
- `한도 초과 → 회수`: 건수와 최단 D-day
- `사용률 저조 → 최적화`: 건수와 최단 D-day
- `조치함 · 재평가 대기`: 건수와 다음 재평가 시각

### 4.2 필터

- 리소스명 검색 (입력 즉시 필터)
- 사유 선택 (전체, 사유 3종)
- 검색어나 사유 필터가 있으면 계정 그룹을 모두 펼쳐서 결과를 보여준다.
- 계정, 프로젝트 필터는 선택 사항이다. 목업에는 없다.

### 4.3 그룹 목록

- 계정 헤더 → 프로젝트 소제목 → 리소스 행 순서다.
- 계정 헤더: 펼침 표시(▾/▸), 계정명, `N건 · 최단 D-n`. 헤더를 누르면 접고 펼친다. 처음에는 첫 계정만 펼친다.
- 프로젝트 소제목: `프로젝트 {이름} · N건`
- 리소스 행의 열 구성
  1. 리소스명 (누르면 상세 패널)
  2. 사유 칩 (`미사용 → 삭제` 등)
  3. 근거 수치 한 줄
  4. D-day 칩과 예정일 (`D-3 10/18`), 또는 `조치함 · 재평가 대기` 칩
  5. 행 액션
- 근거 수치 예시: `미사용 47일`, `한도 대비 120%`, `평균 8% · 최대 21%`
- 기본 정렬은 예정일 오름차순이다. 그룹 안에서도 같다.

### 4.4 행 액션

- 아직 조치하지 않은 행에는 **사유별로 가장 알맞은 조치 하나만** 링크 버튼으로 둔다.
  - 미사용: `재배포 ↗`
  - 한도 초과: `한도 조절 ↗`
  - 사용률 저조: `한도 조절 ↗`
- 나머지 조치는 상세 패널에서 보여준다.
- `조치함 · 재평가 대기` 행에는 링크 버튼 대신 `상세` 버튼을 둔다. 행 배경은 옅은 파랑이다.

### 4.5 D-day 표시

- 예정일까지 7일 이하이면 빨간 칩(`hot`), 그보다 길면 회색 칩이다.
- 칩에는 항상 `D-n` 텍스트가 있어야 한다. 색으로만 구분하지 않는다.
- 조치함 행은 D-day 칩 대신 `조치함 · 재평가 대기` 칩을 보여준다.

## 5. 리소스 상세 패널

위에서 아래로 다음 순서다.

1. 리소스명, `계정 › 프로젝트`, 사유 칩, 조치함이면 상태 칩.
2. 예정 박스: 큰 `D-n`(7일 이하는 빨강), `MM/DD {예정 조치} 예정`, `다음 재평가 {시각}`. 조치함이면 `이 재평가에서 해제될 수 있어요`를 덧붙인다.
3. 사용률 근거 (최근 30일)
   - 한도 초과, 사용률 저조: `CPU / 메모리` 탭과 일별 라인 차트. 차트 규칙은 `metric-chart-guide.md`를 따른다. 단, 이 패널의 차트는 **리소스 한 건**의 지표이고 평균(굵은 선)과 최대(얇은 선) 두 개만 그린다.
   - 미사용: 차트 대신 `미사용 N일 · 이 기간 사용 기록이 없어요`.
4. 진행 이력 타임라인: 회수 대상 선정, 알림 발송, (조치함이면) 재평가 예정. 점과 한 줄 설명이고 시각은 `MM/DD` 형식이다.
5. 조치하기

| 사유 | 주 버튼(채움) | 보조 버튼(외곽선) |
|---|---|---|
| 미사용 | 재배포하기 ↗ | 삭제하러 가기 ↗ |
| 한도 초과 | 한도 조절하기 ↗ | 자원 협의 신청 ↗ |
| 사용률 저조 | 한도 조절하기 ↗ | 자원량 자동조정 (조건부) |

- 자원량 자동조정은 사용량이 기준치 이하이면 **숨기지 않고 비활성**으로 두고, 이유를 한 줄로 적는다. 예: `사용량이 기준치 이하라 자동조정을 쓸 수 없어요.`
- 하단 안내: `조치하면 다음 재평가에서 확인돼요. 예외가 필요하면 관리자에게 문의하세요.`

### 링크 이동 대상

- 직접 삭제, 재배포: 리소스 앱 관리 서비스
- 한도 조절: 계정 상세 › 자원관리 메뉴
- 자원 협의: 자원 협의 메뉴
- 자원량 자동조정: 이동 방식이 정해지지 않았다. (7장 참고)
- 링크는 계정, 프로젝트, 리소스가 **미리 선택된 상태**로 열리는 것이 이상적이다. 대상 서비스가 URL 파라미터로 받는지 확인이 필요하다.

## 6. 처리 이력 탭

- 완료된 건을 보여주는 읽기 전용 목록이다. 행에 조치 버튼은 없다.
- 열 구성: 처리 일시 / 리소스(이름과 `계정 › 프로젝트`) / 사유 → 조치 칩 / 결과 칩 / 처리 방식
- 결과 칩 두 종류
  - `{예정 조치} 완료` (회색): 삭제 완료, 회수 완료, 최적화 완료
  - `회수 해제` (초록): 재평가에서 사유가 해소되어 대상에서 빠진 건
- 처리 방식 예: `회수 배치`, `유저 직접 삭제`, `한도 조절 후 재평가`, `재배포 후 재평가`
- 상단에 `최근 [N]일` 안내를 둔다. **보관 기간은 아직 정해지지 않았으므로** 값은 정책에 따른다. 확정되면 문구를 바꾼다.
- 기본 정렬은 처리 일시 내림차순이다.

## 7. 상태별 화면

### 비어 있는 상태

- 회수 예정 탭: 체크 아이콘, `회수 예정인 리소스가 없어요`, `지금은 조치할 리소스가 없어요. 새로 선정되면 알림으로 알려드려요.` 요약 카드와 필터는 숨긴다.
- 처리 이력 탭: `아직 처리된 이력이 없어요`, `회수가 실행되거나 해제된 리소스가 여기에 쌓여요.`
- 필터 결과 없음: `조건에 맞는 리소스가 없어요`, `검색어나 필터를 바꿔보세요.`와 `필터 초기화` 버튼. 요약 카드와 필터는 유지한다.

### 로딩, 오류 (목업에 없음)

- 로딩: 요약 카드 4개와 목록 영역을 스켈레톤으로 채워 레이아웃이 튀지 않게 한다.
- 조회 실패: 목록 영역에 오류 문구와 `다시 시도` 버튼을 둔다.
- 상세 패널 로딩: 패널은 먼저 열고 본문만 스켈레톤으로 채운다.

## 8. 백엔드 협의가 필요한 사항

### 8.1 상태 추가: `조치함 · 재평가 대기`

- 이 화면은 조치를 링크로만 안내하므로 **유저가 조치했는지 화면은 알 수 없다**.
- 목업은 백엔드가 조치를 감지해서 기록하는 안으로 그렸다. 이 경우 아래 API 필드가 필요하다.
- 백엔드가 감지할 수 없으면 **단순안**으로 간다.
  - `조치함 · 재평가 대기` 상태, 요약 카드 네 번째 칸, 행의 상태 칩, 상세 패널의 `조치함` 문구를 모두 뺀다.
  - 모든 행과 상세에 `다음 재평가 {시각}`만 보여주고, 상세 하단에 `조치하면 다음 재평가에서 확인돼요`를 고정 문구로 둔다.
  - 요약은 사유별 건수만 둔다.

### 8.2 목록·상세 응답 필드 (필드명은 제안)

- `reason`: 미사용, 한도 초과, 사용률 저조
- `plannedAction`: 삭제, 회수, 최적화
- `reclaimStatus`: 회수 예정, 조치함·재평가 대기 (기존 상태값과 매핑)
- `scheduledAt`: 회수 예정일
- `nextReevaluationAt`: 다음 재평가 예정 시각
- `userAction`: 없으면 null. `type`(삭제, 재배포, 자동조정, 한도 조절, 협의 신청), `actedAt`, `actedBy`
- `autoAdjust.available`, `autoAdjust.unavailableReason`: 자동조정 가능 여부와 불가 사유
- `evidence`: 사유별 근거 수치 (미사용 일수, 사용률 평균/최대, 한도 대비 사용률)
- 계정, 프로젝트, 리소스의 ID와 이름

### 8.3 이벤트 이력

- 기존 이벤트에 추가할 타입: `USER_ACTION`(조치 유형, 수행자, 시각), `REEVALUATED`(결과: 해제 또는 유지, 평가 시각), `RELEASED`(회수 대상 해제)

### 8.4 요약, 집계

- 사유별 건수와 최단 `scheduledAt`
- 조치함·재평가 대기 건수
- 계정별, 프로젝트별 건수와 최단 `scheduledAt`

### 8.5 조회 조건

- 필터: 사유, 계정, 프로젝트, 리소스명
- 기본 정렬: `scheduledAt` 오름차순
- 개인당 대상 리소스는 수천 개 미만이다. 서버 페이징이나 가상 스크롤이 필요하다.

### 8.6 처리 이력 API

- 처리 일시, 리소스 경로, 사유와 예정 조치, 결과(실행 완료 또는 해제), 처리 방식
- 최신순 정렬, 기간 필터. 보관 기간은 미정이다.

### 8.7 리소스 단위 메트릭

- 상세 패널의 차트용으로 리소스 한 건의 최근 30일 일별 지표가 필요하다. 필드는 `metric-chart-guide.md` 2장의 명세를 따르되 CPU, 메모리 한도와 평균/최대 사용률이 일자별로 내려와야 한다.

## 9. 아직 정해지지 않은 것

- 처리 이력 보관 기간
- 상태, 사유, 조치 라벨의 최종 용어 (목업의 문구는 임시다)
- 자원량 자동조정의 이동 방식 (다른 서비스 링크인지, 이 화면 안에서 실행인지)
- 링크의 URL 파라미터 지원 여부
- 계정, 프로젝트 필터를 둘지 여부
- 알림 시점과 화면 D-day의 정합성은 백엔드가 판단한다.

## 10. 구현 시 지킬 것

- 사유 칩 색: 미사용(회색), 한도 초과(주황), 사용률 저조(초록). 모든 칩에 텍스트가 있어 색만으로 구분하지 않는다.
- 파랑 계열은 조치함 상태와 링크 버튼에만 쓴다. 빨강은 D-7 이하 임박 표시에만 쓴다.
- 링크 버튼은 `<a>`, 상태 전환은 `<button>`을 쓴다. 아이콘만 있는 버튼에는 `aria-label`을 둔다.
- 계정 헤더는 `aria-expanded`를 갖는다. 상세 패널은 `role="dialog"`와 Esc 닫기를 지원한다.
- 차트 컨테이너에는 `role="img"`와 요약 `aria-label`을 둔다.
- 좁은 화면에서는 요약 카드를 2열로, 행의 열 구성을 세로 쌓기로 바꾼다.

## 11. 완료 기준

- 목업과 나란히 놓았을 때 레이아웃, 칩 색, 요약 카드, 행 구성이 같다.
- 사유별로 서로 다른 조치 링크가 나온다. 한도 초과 건에 자동조정이 나오지 않는다.
- 자동조정이 불가할 때 비활성과 이유가 보인다.
- 빈 상태, 필터 결과 없음, 로딩, 오류 상태가 처리된다.
- 처리 이력 탭이 읽기 전용으로 동작한다.
