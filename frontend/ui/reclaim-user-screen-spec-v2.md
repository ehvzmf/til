# 자원회수 유저 화면 스펙 (v2)

> 변경 이력: 할당량 섹션과 자동조정 가능 여부, 관리자 전용 구역, 안내 문구 톤(정중한 공식 톤)이 반영되었다.

시각 기준은 같은 폴더의 `reclaim-user-mockup.html`이다. 구현 전에 브라우저에서 열어 맞춰 볼 것.
목업 상단의 `목업 옵션`으로 기본 상태와 빈 상태, 권한(유저, 관리자)을 전환할 수 있고, 리소스명을 누르면 상세 패널이 열린다.
목업의 이름, 수치, 날짜, env 값(dev, stg, prod), config 이름은 모두 샘플이다.

## 1. 개요

- 자원관리 계정 앱의 회수 기능 중 **유저 대상 화면**이다. 관리자 화면(정책 관리, 선정 이력, 실행 이력)과는 별개다.
- 유저가 보려는 것은 "내 리소스 중 무엇이, 언제, 왜, 어떻게 되는가, 내가 무엇을 할 수 있는가"이다.
- 이 화면은 **현황을 보여주고 알맞은 곳으로 보내는 화면**이다. 조치 자체는 다른 서비스에서 일어나며 이 화면에는 조치 로직이 없다.

## 2. 용어와 규칙

- 위계: 계정 › 프로젝트 › 리소스. 리소스에는 **서비스 타입**과 **플랫폼**(플랫폼 A, 플랫폼 B)이 있다.
- 회수 사유와 예정 조치는 항상 한 쌍으로 표시한다.
  - 미사용 → 삭제
  - 한도 초과 → 회수
  - 사용률 저조 → 최적화
- 상태는 네 가지다.
  - `회수 예정`: 아직 회수 전이다. `회수 예정` 탭에 보인다.
  - `회수 완료`: 회수 배치가 실행되어 끝난 건이다.
  - `취소`: 관리자가 요청을 받거나 해서 취소한 건이다.
  - `철회`: 재평가에서 사유가 해소되어 회수 대상에서 거둔 건이다.
  - 회수 완료, 취소, 철회는 `처리 이력` 탭에 보인다.
- 선정 주기, 회수 배치, 재평가 주기는 정책의 cron으로 돈다. 유저가 조치해도 회수 예정은 바로 해제되지 않고 **다음 재평가**에서 판단된다.
- 조치한 건의 재평가는 회수 배치보다 먼저 실행되는 것으로 가정한다.
- 유예 기능은 없다. 유저의 조치가 곧 유예 역할이다.
- 예외 신청은 관리자 화면에서 한다. 유저 화면에는 `예외가 필요한 경우 관리자에게 문의 부탁드립니다.` 안내 문구만 둔다.
- 목록은 로그인한 유저의 권한이 있는 리소스만 내려온다. 화면에서 권한 체크는 하지 않는다.
- **사용률 저조 판단 기준**은 CPU 10%, 메모리 30%가 일반적이고 상세 조회 응답에 함께 내려온다. 화면에 값을 하드코딩하지 않는다.

## 3. 화면 구조

- 네비게이션의 `자원회수` 독립 메뉴다. 진입하면 바로 이 화면이 나온다.
- 상단에 제목과 한 줄 설명(`회수 예정인 리소스를 확인하시고 조치 부탁드립니다. 조치 후 다음 재평가에서 반영됩니다.`)을 둔다.
- 탭 두 개: `회수 예정 N`(기본), `처리 이력`.
- 리소스 상세는 오른쪽에서 열리는 패널(너비 500px)이다. 오버레이를 누르거나 Esc나 × 버튼으로 닫는다.
- 조치 버튼은 모두 **다른 서비스로 이동하는 링크**다. 링크 버튼에는 `↗`를 붙인다.
- **문구 톤**: 화면의 모든 안내 문구는 정중한 공식 톤으로 쓴다. 서술은 `~합니다`, `~없습니다`로, 요청은 `~부탁드립니다`, `~해 주시기 바랍니다`로 쓴다. `~해요`, `~없어요` 같은 구어체와 `~하십시오` 같은 명령형은 쓰지 않는다. 이 문서에 인용된 문구가 기준이다.

## 4. 필터 (두 탭 공통, 한 줄)

한 줄에 다음 순서로 둔다. 입력 폭을 작게 해서 1240px 컨테이너 안에 들어가게 하고, 화면이 좁으면 줄바꿈한다.

1. 리소스명 검색 (남는 폭을 모두 쓴다)
2. 회수 사유
3. 결과 (**처리 이력 탭에만** 표시: 회수 완료, 취소, 철회)
4. 계정
5. 프로젝트
6. env
7. 플랫폼
8. 기간 from ~ to: 회수 예정 탭에서는 **회수 예정일**, 처리 이력 탭에서는 **처리일** 기준이다.
9. `초기화` 텍스트 버튼

- 선택 박스는 폭 약 106px, 날짜 입력은 약 128px이다.
- env 필터는 해당 env에 **배포된**(배포 여부가 참인) 리소스만 남긴다.
- 필터가 하나라도 걸리면 계정 그룹을 모두 펼친다. 처리 이력의 `결과` 필터는 이 판단에서 제외한다.
- 필터 값은 두 탭이 공유하되, `결과`는 처리 이력에서만 적용한다.
- 필터 로직은 프론트에서 정의한다. 한 줄 배치가 어려우면 AG Grid의 컬럼 필터로 대체해도 된다. 이 경우 시각 기준은 달라진다.

## 5. 회수 예정 탭

### 5.1 요약 카드 (4개, 4열 그리드)

- `미사용 → 삭제`, `한도 초과 → 회수`, `사용률 저조 → 최적화`: 각각 건수와 최단 D-day
- `조치함 · 재평가 대기`: 건수와 다음 재평가 시각
- 요약은 필터와 무관하게 회수 예정 전체 기준이다.

### 5.2 그룹 목록

- 계정 헤더 → 프로젝트 소제목 → 리소스 행 순서다.
- 계정 헤더: 펼침 표시(▾/▸), 계정명, `N건 · 최단 D-n`. 처음에는 첫 계정만 펼친다.
- 프로젝트 소제목: `프로젝트 {이름} · N건`
- 리소스 행의 열 구성
  1. 리소스명(누르면 상세 패널) + 아래 보조 줄 `서비스 타입 · 플랫폼`과 env 칩
  2. 사유 칩
  3. 근거 수치 (판단 기준 포함)
  4. D-day 칩과 예정일, 또는 `조치함 · 재평가 대기` 칩
  5. 행 액션
- env 칩: 배포 중인 env만 작은 외곽선 칩으로 나열한다.
  - **미사용 → 삭제 건이 prod에 배포 중이면** 해당 칩을 `prod 배포 중`으로 바꾸고 빨간 외곽선과 굵은 글씨로 강조한다. 삭제 예정인데 운영에 배포된 상태는 유저가 가장 먼저 알아야 하는 신호다.
- 근거 수치 예시: `미사용 47일`, `한도 대비 최대 120%`, `CPU 평균 8% (기준 10% 미만)`, `메모리 평균 22% (기준 30% 미만)`
- 기본 정렬은 예정일 오름차순이다.

### 5.3 행 액션

- 아직 조치하지 않은 행에는 **사유별로 가장 알맞은 조치 하나만** 링크 버튼으로 둔다.
  - 미사용: `재배포 ↗`
  - 한도 초과: `한도 조절 ↗`
  - 사용률 저조: `한도 조절 ↗`
- `조치함 · 재평가 대기` 행에는 링크 버튼 대신 `상세` 버튼을 둔다. 행 배경은 옅은 파랑이다.

### 5.4 D-day 표시

- 예정일까지 7일 이하이면 빨간 칩, 그보다 길면 회색 칩이다.
- 칩에는 항상 `D-n` 텍스트가 있어야 한다. 색으로만 구분하지 않는다.

## 6. 처리 이력 탭

- 읽기 전용 목록이다. 행에 조치 버튼은 없다. 리소스명을 누르면 상세 패널이 읽기 전용으로 열린다.
- 상단에 `최근 [N]일 · 보관 기간은 정책에 따릅니다` 안내를 둔다. **보관 기간은 미정**이다.
- 열 구성: 처리 일시 / 리소스(이름, `계정 › 프로젝트 · 서비스 타입 · 플랫폼`) / 사유 → 조치 칩 / 결과 칩 / 처리 방식
- 결과 칩

| 상태 | 칩 문구 | 색 |
|---|---|---|
| 회수 완료 | `삭제 완료`, `회수 완료`, `최적화 완료` (사유별) | 회색 |
| 취소 | `취소` | 보라 |
| 철회 | `철회` | 초록 |

- 처리 방식 예: `회수 배치 실행`, `관리자 요청으로 취소`, `사유 해소 · 한도 조절 후 재평가`, `사유 해소 · 재배포 후 재평가`
- 기본 정렬은 처리 일시 내림차순이다.

## 7. 리소스 상세 패널

위에서 아래로 다음 순서다.

1. **헤더 영역**: 리소스명, `계정 › 프로젝트`, 사유 칩, (조치함이면 상태 칩), 서비스 타입 칩, 플랫폼 칩.
2. **상태 박스**
   - 회수 예정: 큰 `D-n`(7일 이하는 빨강), `MM/DD {예정 조치} 예정`, `다음 재평가 {시각}`. 조치함이면 `이 재평가에서 해제될 수 있습니다`를 덧붙인다.
   - 처리 이력: 결과 칩, 처리 일시, 처리 방식.
3. **배포 상태** 표: 열은 `config / env / 배포 / CPU / 메모리`다.
   - 배포 여부는 `● 배포됨` 또는 `○ 미배포`로 글자와 기호를 함께 쓴다. 미배포 행은 글자색을 흐리게 하고 자원량은 `-`로 둔다.
   - config가 여러 개이면 같은 표에 행으로 늘어난다. 행이 많아지면 config별로 접는 것을 검토한다.
4. **할당량** 표 (7.2 참고)
5. **사용률 근거 (최근 30일)**
   - 한도 초과, 사용률 저조: `CPU / 메모리` 탭과 일별 라인 차트. 차트 기본 규칙은 `metric-chart-guide.md`를 따른다. 이 차트는 **리소스 한 건**의 지표이고 평균(굵은 선)과 최대(얇은 선) 두 개만 그린다.
   - 값이 100%를 넘으면 100%로 표시하고 `100%를 넘는 값은 100%로 표시됩니다.`를 덧붙인다.
   - 미사용: 차트 대신 `미사용 N일 · 이 기간 사용 기록이 없습니다.`
6. **진행 이력**: 8장 참고.
7. **조치** (회수 예정 건만): 9장 참고. 처리 이력 건에는 `처리가 완료된 건으로 조치할 수 없습니다.`만 보여준다.
8. **관리자 전용** (회수 예정 건이고 관리자일 때만): 9.2 참고.

### 7.2 할당량 표

- 위치: 배포 상태 표 아래, 사용률 근거 차트 위. **배포 상태 표는 config와 env별 배포 현황**이고, **할당량 표는 리소스의 판단 근거 수치**다. 서로 다른 필드이므로 합치지 않는다.
- 행은 `CPU`, `메모리` 두 개다. 열은 `항목 / 현재 할당량 / 필요 할당량 / 최소 할당량 / 사용률 / 저조 기준`이다.
- 데이터는 CPU와 메모리 각각 `currentQuota`, `requiredQuota`, `minQuota`, `usage`(%), `thresholds`로 내려온다.
- **필요 할당량**(`requiredQuota`)은 현재 사용률을 정책 기준치 이상으로 끌어올리는 데 필요한 **최소 할당량**이다. 사용률이 이미 기준 이상이면 현재 할당량과 같은 값이 온다.
- 사용률 저조 건에서만 다음을 표시한다.
  - 사용률이 저조 기준 미만인 행은 사용률 칸에 `8% · 미달`을 굵은 빨간 글씨로 쓴다. 색뿐 아니라 `미달` 글자가 있어야 한다.
  - 현재 할당량이 최소 할당량 이하인 행은 최소 할당량 칸 옆에 `최소 도달` 배지(주황 외곽선)를 붙인다.
  - 표 아래에 `필요 할당량은 사용률을 저조 기준 이상으로 올리는 데 필요한 최소 할당량입니다.`를 둔다.
- 미사용, 한도 초과 건은 필요 할당량 칸을 `-`로 표시하고 위 표시와 안내는 생략한다.

### 7.1 차트의 저조 기준선 (사용률 저조 건에만)

- 판단 기준(`thresholds` 값. 일반적으로 CPU 10%, 메모리 30%)을 **회색 점선**으로 그리고 선 오른쪽에 `기준 10%` 라벨을 붙인다. 선 굵기 1.5px, 점선 `[6, 4]`, 색 `#898781`이다.
- 탭을 바꾸면 기준선도 그 지표의 값으로 바뀐다.
- 기준 미만인 지표의 탭에는 `기준 미달` 문구를 붙인다 (예: `CPU · 기준 미달`). 해당 지표가 둘 다 미달이면 CPU가 먼저다.
- 패널을 열 때 기본 선택 탭은 **기준 미달인 지표**다. 둘 다 미달이면 CPU, 둘 다 아니면 CPU다.
- 차트 위 설명줄: `평균 8% · 최대 21% · 저조 기준 10% 미만`
- 한도 초과 건에는 기준선을 그리지 않는다.

## 8. 진행 이력 (타임라인)

- **최신순**으로 정렬한다. 위쪽이 가장 최근 또는 가장 먼 미래다.
- 아직 오지 않은 이벤트(회수 예정, 다음 재평가)는 **속이 빈 점과 점선**으로 맨 위에 둔다.
- 처리가 끝난 건에서는 **최종 상태(회수 완료, 취소, 철회)가 맨 위의 강조 노드**다. 점이 크고 상태색(회색, 보라, 초록)이며 문구는 굵게 쓴다.
- 각 노드는 두 줄이다. 첫 줄은 `MM/DD 이벤트 유형`, 둘째 줄은 `주체 · 결과 한 줄`이다.
- 이벤트 유형: 회수 대상 선정, 알림 발송 n회차, 재평가 · 유지, 재평가 · 해제(철회), 회수 완료, 취소, 철회, 다음 재평가, {예정 조치} 예정, **회수 예정일 변경, 단계별 감축 즉시 실행, 즉시 회수** (후자 세 개는 관리자 작업이며 주체는 `관리자`)
- 회수 예정일을 변경해도 **과거 이벤트의 날짜는 바뀌지 않는다.** 예정 노드만 새 날짜로 바뀐다.
- 주체: 시스템, 관리자, 유저
- 이력이 쌓이면 **최근 5건만** 보여주고 `전체 이력 N건 보기` 버튼으로 펼친다. 펼치면 `접기`로 바뀐다. 제목 옆에 전체 건수를 `· N건`으로 표시한다.
- 취소와 철회의 노드에는 사유를 한 줄로 보여준다 (예: `관리자 · 요청 접수 후 취소`, `시스템 · 사유 해소로 회수 대상에서 해제`).

## 9. 조치

### 9.1 유저 조치

| 사유 | 주 버튼(채움) | 보조 버튼(외곽선) |
|---|---|---|
| 미사용 | 재배포 ↗ | 삭제 ↗ |
| 한도 초과 | 한도 조절 ↗ | 자원 협의 신청 ↗ |
| 사용률 저조 | 한도 조절 ↗ | 자원량 자동조정 (조건부) |

- 하단 안내: `조치하면 다음 재평가에서 확인됩니다. 예외가 필요한 경우 관리자에게 문의 부탁드립니다.`
- 링크 이동 대상
  - 삭제, 재배포: 리소스 앱 관리 서비스
  - 한도 조절: 계정 상세 › 자원관리 메뉴
  - 자원 협의: 자원 협의 메뉴
  - 자원량 자동조정: 이동 방식 미정
- 링크는 계정, 프로젝트, 리소스가 미리 선택된 상태로 열리는 것이 이상적이다. URL 파라미터 지원 여부는 확인이 필요하다.

#### 자원량 자동조정

- 사용 가능 여부는 백엔드가 `eligible`로 내려준다. 화면에서 직접 판단하지 않는다.
- `eligible: true`
  - 활성 링크 버튼으로 표시한다.
  - 버튼 아래에 **예상 조정 결과**를 한 줄로 보여준다. 항목별로 `requiredQuota`가 `currentQuota`보다 작으면 `CPU 2.5 → 2.25 core`처럼, 같으면 `CPU 변경 없음`으로 쓴다. 구분자는 ` / `이다. 필요 할당량은 사용률을 저조 기준 이상으로 올리는 데 필요한 최소 할당량이므로 실제 조정값과 다를 수 있다. 확정 전에 백엔드에 확인한다.
- `eligible: false`
  - **숨기지 않고 비활성**으로 표시하고 버튼 오른쪽에 `사용 불가`를 쓴다.
  - 버튼 아래에 `reasonCode`에 대응하는 문구를 보여준다. 문구는 프론트의 매핑 표 한 곳에서 관리한다.

| reasonCode | 문구 |
|---|---|
| `min-quota-floor` | 현재 자동조정을 사용할 수 없습니다. 할당량이 이미 최소 할당량에 도달했습니다. |
| (그 외, 미정의 코드) | 현재 자동조정을 사용할 수 없습니다. |

- 사유 코드는 총 3종이다. 현재는 `min-quota-floor`만 설계하고, 나머지 두 개는 코드가 확정되면 표에 추가한다.

### 9.2 관리자 전용 구역

- **관리자만 조회**할 수 있다. 관리자 여부는 세션이나 백엔드 값으로 판단하고, 일반 유저에게는 구역 자체가 렌더링되지 않는다.
- 위치는 상세 패널 맨 아래이며, 유저 조치와 구분되도록 **점선 박스**와 `관리자 전용 · 일반 사용자에게는 표시되지 않습니다` 제목을 둔다.
- 회수 예정 건에만 표시한다. 회수 완료, 취소, 철회 건에는 표시하지 않는다.
- 버튼은 가벼운 것부터 위험한 순서로 세로 배치한다.

| 순서 | 버튼 | 동작 |
|---|---|---|
| 1 | 회수 예정일 수정 | 모달에서 새 예정일을 변경한다. |
| 2 | 단계별 감축 즉시 실행 | 확인 모달 후 단계별 감축의 다음 단계를 즉시 실행한다. |
| 3 | 즉시 회수 (리소스 중지) | 확인 모달 후 리소스를 즉시 중지하고 회수한다. 빨간 글씨와 빨간 외곽선으로 구분한다. |

#### 회수 예정일 수정 모달

- 상단: 리소스명, 현재 예정일(`MM/DD (D-n)`), `다음 재평가 {시각} 이후의 날짜만 선택할 수 있습니다.`
- 입력: 새 예정일(날짜), 변경 사유(여러 줄, 필수, placeholder `변경 사유를 입력해 주시기 바랍니다`)
- 새 예정일을 고르면 `D-5 → D-12 (10/30)`처럼 변경 결과를 즉시 보여준다.
- 새 예정일은 다음 재평가 시각 **이후** 날짜만 허용한다 (재평가가 회수 배치보다 먼저 실행된다는 전제).
- `저장`은 날짜가 바뀌고 사유가 있을 때만 활성화된다.
- 저장하면 목록과 상세의 D-day가 바로 바뀌고, 진행 이력에 `회수 예정일 변경 · 관리자 · 10/20 → 10/30 · {사유}`가 남는다.

#### 단계별 감축 즉시 실행 모달

- 문구: `{리소스명}의 단계별 감축 중 다음 단계를 즉시 실행합니다.` / `실행 내용은 진행 이력에 기록됩니다.`
- 버튼: `취소`, `실행`
- 실행하면 진행 이력에 `단계별 감축 즉시 실행 · 관리자 · 다음 단계 실행`이 남는다.

#### 즉시 회수 모달

- 해당 리소스가 **prod 환경에 배포 중이면** 상단에 빨간 경고 박스를 둔다: `prod 환경에 배포 중입니다. 실행하면 운영 중인 서비스가 중단됩니다.`
- 문구: `{리소스명}을(를) 즉시 중지하고 회수합니다.`
- **리소스명을 직접 입력해야** `즉시 회수` 버튼(빨간 채움)이 활성화된다.
- 실행하면 상태가 `회수 완료`가 되어 처리 이력으로 이동하고, 최종 노드가 `회수 완료 · 관리자 · 즉시 회수 (리소스 중지)`로 표시된다.

## 10. 상태별 화면

- 회수 예정 탭이 비어 있음: 체크 아이콘, `회수 예정인 리소스가 없습니다`, `현재 조치할 리소스가 없습니다. 새로 선정되면 알림으로 안내드립니다.` 요약과 필터는 숨긴다.
- 처리 이력 탭이 비어 있음: `처리된 이력이 없습니다`, `회수가 완료되거나 취소, 철회된 리소스가 여기에 표시됩니다.`
- 필터 결과 없음: `조건에 맞는 리소스가 없습니다`(이력은 `이력이`), `필터를 변경해 주시기 바랍니다.`와 `필터 초기화` 버튼. 요약과 필터 줄은 유지한다.
- 로딩(목업에 없음): 요약 카드와 목록을 스켈레톤으로 채워 레이아웃이 튀지 않게 한다. 상세 패널은 먼저 열고 본문만 스켈레톤으로 채운다.
- 조회 실패(목업에 없음): 목록 영역에 오류 문구와 `다시 시도` 버튼을 둔다.

## 11. 데이터

- 서비스 타입, 플랫폼, 배포 상태(config, env별 배포 여부, CPU와 메모리 자원량), 사유, 상태, 일자별 지표, 근거 수치, 자동조정 가능 여부(`eligible`, `reasonCode`), CPU와 메모리 각각의 `requiredQuota`, `currentQuota`, `minQuota`, `usage`, `thresholds`는 **백엔드가 이미 내려주고 있다**.
- **새로 필요한 것은 진행 이력 이벤트뿐이다.** 이벤트마다 다음이 필요하다.
  - 유형: 선정, 알림 발송(회차), 재평가(결과: 유지 또는 해제), 회수 완료, 취소, 철회, 회수 예정일 변경, 단계별 감축 즉시 실행, 즉시 회수
  - 발생 시각
  - 주체: 시스템, 관리자, 유저
  - 한 줄 결과 설명 (예: 기준 미달 지속, 요청 접수 후 취소)
- 조치함 상태(`조치함 · 재평가 대기`)는 백엔드가 유저 조치를 감지해야 쓸 수 있다. 감지가 불가능하면 단순안으로 간다.
  - `조치함` 상태, 요약 카드의 네 번째 칸, 행의 상태 칩, 상세의 `조치함` 문구를 뺀다.
  - 모든 행과 상세에 `다음 재평가 {시각}`만 보여주고, 요약은 사유별 건수만 둔다.
- 회수 예정일 수정, 단계별 감축 즉시 실행, 즉시 회수는 관리자 전용 기능이다. 요청 API와 응답 형식은 별도 확인이 필요하다.
- 필터 조건은 프론트에서 정의한다. 개인당 대상 리소스는 수천 개 미만이므로 서버 페이징이나 가상 스크롤이 필요하다.

## 12. 아직 정해지지 않은 것

- 처리 이력 보관 기간
- 상태, 사유, 조치, 이벤트 유형의 최종 용어 (목업의 문구는 임시다)
- env 값의 실제 목록 (목업은 dev, stg, prod)
- config와 env가 조합될 때 배포 상태 표가 길어질 경우의 접기 방식
- 자원량 자동조정의 이동 방식, 그리고 실제 조정값이 `requiredQuota`와 같은지 여부 (예상 조정 결과 문구에 영향)
- 자동조정 불가 사유 코드 두 개 (미정의 코드는 일반 문구로 대체)
- 단계별 감축의 단계 정보 (현재 몇 단계인지, 다음 단계가 무엇인지)가 내려오는지. 내려오면 모달과 상세에 표시한다.
- 단계별 감축 즉시 실행이 사유 전체에 해당하는지, 사용률 저조(최적화) 건에만 해당하는지. 목업은 모든 회수 예정 건에 세 버튼을 모두 표시한다.
- 즉시 회수 후 처리 이력에서의 결과 칩 문구 (목업은 `{조치} 완료`)
- 링크의 URL 파라미터 지원 여부
- 처리 이력의 기간 필터가 처리일 기준이라는 점의 최종 확인
- 알림 시점과 화면 D-day의 정합성은 백엔드가 판단한다.

## 13. 구현 시 지킬 것

- 관리자 구역의 `즉시 회수` 버튼과 모달 경고에만 빨강 채움 또는 외곽선을 쓴다.
- 사유 칩 색: 미사용(회색), 한도 초과(주황), 사용률 저조(초록). 결과 칩 색: 회수 완료(회색), 취소(보라), 철회(초록). 모든 칩에 텍스트가 있어 색만으로 구분하지 않는다.
- 파랑 계열은 조치함 상태, 링크 버튼, 진행 이력의 일반 노드에만 쓴다. 빨강은 D-7 이하 임박 표시와 `prod 배포 중` 강조에만 쓴다.
- 링크 버튼은 `<a>`, 상태 전환은 `<button>`을 쓴다. 아이콘만 있는 버튼에는 `aria-label`을 둔다.
- 필터 입력에는 `aria-label`을 둔다. 날짜 입력은 시작과 끝을 구분해서 라벨을 단다.
- 계정 헤더는 `aria-expanded`를 갖는다. 상세 패널은 `role="dialog"`와 Esc 닫기를 지원한다.
- 차트 컨테이너에는 `role="img"`와 요약 `aria-label`을 둔다. 저조 기준값도 라벨에 포함한다.
- 좁은 화면에서는 요약 카드를 2열로, 행의 열 구성을 세로 쌓기로 바꾼다.

## 14. 완료 기준

- 목업과 나란히 놓았을 때 필터 줄, 행의 보조 줄과 env 칩, 요약 카드, 상세 패널의 섹션 순서가 같다.
- 사용률 저조 건의 차트에 기준선과 `기준 미달` 탭 표시가 나오고, 기본 탭이 기준 미달 지표다.
- 진행 이력이 최신순이고 예정 노드는 점선이며, 5건을 넘으면 접힘과 펼침이 된다.
- 처리 이력의 결과 칩과 상세가 읽기 전용으로 동작하고, 상태별(회수 완료, 취소, 철회) 최종 노드가 다르게 보인다.
- 필터 8종이 동작하고, 필터 결과 없음과 빈 상태, 로딩, 오류가 처리된다.
- 한도 초과 건에 자동조정이 나오지 않는다.
- 자동조정이 불가할 때 비활성과 `reasonCode`별 문구가 보이고, 가능할 때 예상 조정 결과가 보인다.
- 할당량 표에서 저조 건의 `미달`, `최소 도달` 표시가 나온다.
- 관리자 구역이 관리자에게만 보이고, 세 버튼의 모달이 각각 동작하며, 실행 결과가 진행 이력에 남는다.
- 모든 안내 문구가 정중한 공식 톤이다. 명령형(`~하십시오`)이 없다.
